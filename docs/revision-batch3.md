## Critical Gaps & Improvement Suggestions

* **Quotation Builder**:  The current UI only lets users pick a matrix and parameter; it doesn’t support sub‑parameters (e.g., heavy‑metal panels) or test packages as described in the flow.  The “LineItemManager” should allow adding sub‑parameters or selecting a package, and display due‑date estimates per line item (based on turnaround time rules) rather than only “lead_time_days”.  A quick filter for packages would make quoting faster.

* **Quotation & Contract Review Workflow**:  There is no dedicated queue for quotations awaiting review; managers must find them from the general list.  A “Contract Review” queue (similar to results‑review) would improve usability and align with the flow.  The review checklist should also include explicit fields for decision rule acceptance and turnaround feasibility, as per the blueprint.

* **Receiving Wizard**:  The wizard captures sampling details and CoC, but lacks fields for sample quantity & unit, packaging type, condition upon receipt (intact/leak/damaged), and storage location/condition—all required in the blueprint.  It also does not record acceptance/rejection criteria or chain‑of‑custody logs.  Adding these will ensure the sample receipt meets ISO‑17025 requirements.

* **Scheduling**:  Task generation currently uses mock requested tests and doesn’t pull actual requested tests from the work order.  The UI should display the requested tests fetched from the linked quotation or work order, allow due‑date overrides per test, and flag if analysts are unqualified for a method/instrument.  A calendar or Gantt‑style view could improve resource planning.

* **QC Monitoring**:  The QC monitor page displays control charts but doesn’t yet implement trending across the “last 5 samples” or provide warnings when recovery falls outside 80–120 % (the blueprint’s default).  Implementing dynamic QC alerts and letting users drill into flagged runs will make it useful.

* **Revision Loop**:  There is no UI for the strict revision loop.  When a manager requests a revision during review, the system should create a revision request, mark tasks as “IN_PROGRESS/WAITING_RECHECK”, and show the history.  Adding a small revision tab or modal in the review detail panel can handle this.

* **Report & Approval Flow**:  The report builder supports multi‑sample selection and signatures, but there is no intermediate step for “Submit Results” (analyst) and “Review Queue” (manager).  Ensure the worklist has a “Submit for review” action that validates that all tests are completed and QC records are entered, and moves the work order into the review queue.

* **Portal Functionality**:  The customer portal currently shows status dashboards and individual report views, but the blueprint also calls for search by report number, sample name, date range and bulk download (ZIP).  These search & bulk download features are not present and need to be added.

* **Master Data & Settings**:  The “Settings” route is a placeholder.  To support the flows, there must be pages to manage departments, users (Admin/Manager/Analyst), customer contacts, matrices, parameters, methods, instruments, units, matrix‑parameter rules, price lists and test packages.  Without these, the auto‑populate logic in the UI will rely on mock data.

* **Audit Trails & Versioning**:  UI components log audit events locally (e.g., run management), but there’s no consolidated audit trail viewer.  Consider adding a route under settings or work orders to view the full audit history (created_by, updated_by, before/after values) and report version history as required by the anti‑silent‑edit principle.

Addressing these gaps will bring the UI/UX closer to the operational blueprint and ensure that future integrations (e.g., database, authentication) have the necessary screens to support end‑to‑end LIMS workflows.
